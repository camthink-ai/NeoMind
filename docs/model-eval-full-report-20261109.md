## 一、执行摘要

在 1.2.6 冻结二进制上，以统一 138 例双语硬信号门禁对 9 个本地模型（10 个配置臂）完成全量重测，并首次携带单步/多步分层、到正确终态墙钟延迟、确定性失败模式分类三列新维度。

**六条核心结论：**

1. **Spark-X2.6-4B（思考开）以 75.4% 居首，与 10-29 的"4B 不如自家 1.7B"方向相反**（59.4% → 75.4%）；多步 60.0% 领先第二名 12.5pp，代价仅为 27→51 秒的中位延迟。**但对 1.7B 的逐案配对为 17 增/7 退（McNemar p≈0.064），属未统计确认的候选优势**；且跨批对比含采样条件差异（见第 2 条）。
2. **与 10-29 相比各配置普遍走高 3~17pp，但这是历史关联、非受控归因**：两批之间采样参数取法、量化与运行条件存在差异（尤其 Spark 系本批首次全程使用官方参数 1.0/0.95），代码提升的份额需受控对照才能隔离。LFM3 +17.4pp 同理仅记录现象，其"多步死穴"旧结论与新数据（multi 47.5%）不一致这一点是可靠的。
3. **Spark-1.7B 仍是"最快最稳"档**：27 秒到正确终态（全场最快）、零超时；Spark 系独有 rejected_args 主导的失败画像（参数精度而非工具选择问题）。
4. **新选手画像分化**：Nanbeige4.2-3B 思考开 60.1%（**23 例全部为 600s 预算超限**，重标后无真实流中断；其 diagnostic 72.2% 因剔除这 23 例、剩余案例偏易而存在**选择偏差**，不能据此称"能力第二"），思考关是实用档（57.2% / 97 秒 / 5 例超时）；Ling-3.0-tiny（1B 激活 MoE）"快稳中场"（55.1% / 36 秒 / 1 例超时）。
5. **到正确终态延迟拉开了同分模型的真实差距**：同为 ~55~59% 档，Qwen 28 秒 vs Granite 91 秒 vs Nanbeige-on 175 秒——通过率看不见的速度差超过 6 倍。
6. **失败模式分类首次给出"每模型该修什么"**：Spark 系修参数（rejected_args）、LFM2.5 思考关修工具选择（wrong_tool 24 例）、其余模型主攻 missing_tool（没找到正确工具族）。

### 3.3 新增指标定义

- **simple/multi 分层**：case-id 前缀 `multi/guided/deep/full-lifecycle/agent/extension/api/haccp` 为多步层（20/69 × 双语 = 40 执行），与 10-29 报告口径逐位一致。
- **到正确终态延迟（time-to-pass）**：仅对 product 口径 PASS 的执行取中位；数值为该 case 全部 turn 的服务端处理时长之和（ReAct 内部重试耗时天然包含，播种/起服不含）。
- **失败模式（一失败一标签，优先级序）**：`timeout → agent_error → harness_error → wrong_tool → missing_tool → rejected_args → wrong_args → state_mismatch → other`；"丢上下文"需语义判定，按设计留给可选 judge 维度，不在硬信号内。

## 五、分模型速评

- **Spark-X2.6-4B（本批最优，未统计确认）**：多步 60.0% 断层第一，zh/en 双高，仅 2 例超时；失败少而分散。对 1.7B 逐案配对 17 增/7 退（p≈0.064）——候选优势，需 rounds=2 确认。51 秒中位延迟是唯一代价。
- **Spark-X2.6-1.7B（速度/可靠性之王，默认候选）**：27 秒、零超时，rejected_args 22 例是其主要失分点——"命令族对、旗标错"，提示 CLI 参数提示词或错误恢复提示仍有小分可挖。
- **LFM3-1.7B（旧结论需重验）**：multi 47.5% 跃居第二，但 130 秒延迟 + 9 例 600s 超时；官方低温参数（0.1）下稳定。
- **Nanbeige4.2-3B（预算受限型）**：思考开 60.1%，23 例全部为 600s 预算超限（非流中断；diagnostic 72.2% 有选择偏差不作能力论据）——在 600s 服务预算内思考链跑不完是其真实交付限制；思考关（57.2% / 97 秒 / 5 例超时）是可部署档位。长预算表现需预注册的独立实验，不能从本批分数外推。
- **Qwen3.5-4B（均衡快枪）**：28 秒 + 1 例中断 + multi 45.0%，输在单步精度（65.3% vs Spark 系 78+）。
- **Granite-4.2-3B（无思考模式的扛把子）**：后端不支持思考的纯直答模型拿 56.5% + multi 40.0%，T4 比自家 Mac 基线高 2.9pp。
- **MiniCPM5-2B / Ling-3.0-tiny（同分不同性格）**：同为 55.1%，MiniCPM5 靠思考链（79 秒），Ling 靠 1B 激活 MoE 的速度（36 秒、近零中断）；Ling 是"响应速度敏感场景"的优选。
- **LFM2.5-2.6B 思考关（垫底且有独有病灶）**：multi 15.0% 全场最低，wrong_tool 24 例独此一家——无思考时大量抓 file_write/web_fetch 类错误工具。

## 七、结论与建议

1. **产品选型**：Spark-1.7B 适合作为当前**默认候选**，Spark-4B 适合作为**更重任务的候选**——本轮支持该取舍方向，但未验证自动路由收益，也不足以宣布 4B 全面替代 1.7B；4B 领先的统计确认（rounds=2 或任务聚类校正）是下一步验证项，不是本轮结论。
2. **超时计入产品失败、不剔除**：600s 预算下未完成即该配置的实际交付限制（本批诊断口径仅作参考，且 Nanbeige 的 diagnostic 存在选择偏差）。若要评估长预算表现，按迭代协议做预注册的长预算独立实验，不改本批总分。
3. **旧结论修订**：10-29 中 LFM3"多步死穴"、Spark-4B"不如 1.7B"两条与新数据不一致，列为"待受控重验"而非直接反转；README 目录卡措辞随本报告更新。
4. **工程跟进**：① **错误恢复闭环**（运行时）：部分模型在工具失败后重复同类失败、恢复提示未有效改变行为——先取真实轨迹确认模型是否看到提示/提示是否截断/是否指明本次具体错误，再做小范围修复，不直接堆提示词；② CLI 报错改善：双重 `error:` 前缀、usage 行不完整、`--name`/`--body` 互斥易混用（本批 rule create 失败调用 312 次：unexpected-argument 134、其他 clap 99、互斥 64、无 stderr 15——**这些标签用于筛轨迹，产品修复方向需先完成失败原因细分审计**）；③ LFM2.5 思考关 wrong_tool 24 例（筛轨迹性质）；④ paddle-ocr 扩展 GPU 常驻加载策略（本次靠守卫兜底，建议按需加载或显存上限）。
5. **评估器已完成修复（工作区，待提交）**：超时透传+抢救保留、逐例完整 wall-clock（elapsed_ms）、失败命令原因细分（failed_cmd_reasons）、历史独立重标工具。控制器侧（带哈希校验的断点续跑、队列/显存运维项）为下一批前待办。
6. **榜单口径**：本批为单轮、官方参数、1.2.6 冻结二进制；跨批比较必须同时携带 controls 与运行条件差异说明（见第 2 条：本批 vs 10-29 为历史关联）。
