## 2. PR 1：运行期事件触发与稳定性根治（P0）

### 2.1 A1：补齐整设备快照与手动执行采集（含 M2-1 `any`/`all` 与 `ResourceType::Device`）

- **问题根因**：
  - `crates/neomind-agent/src/ai_agent/executor/data_collector.rs`（`collect_single_device_data`）硬编码的 `image_metric_names` 漏掉 `"image_data"`。
  - 整设备监听触发时，运行期只围绕“抢先到达的那一个字段”拼装输入，未主动拉齐该设备当前完整快照。
  - `crates/neomind-agent/src/ai_agent/executor/event_trigger.rs`（`extract_trigger_candidates` / `build_synthetic_event_data`）存在三处缺口：
    1. 手写读取旧版 `filter.get("sources")`，未复用 `agent.schedule.parsed_event_filter()`，导致 M2-1 `{"any":[...]}` / `{"all":[...]}` 事件型 Agent 手动执行拿不到候选源；
    2. 跳过 `s_field.is_empty()`，导致整设备监听事件型 Agent 点击「立即运行（Run now）」无合成事件；
    3. 资源回退分支只匹配 `ResourceType::Metric` 与 `ResourceType::ExtensionMetric`，**跳过了 `ResourceType::Device`**（通过 `--device-ids` 绑定的整设备资源），导致仅用 `--device-ids` 绑定的事件型 Agent 在 Run now 时仍无合成事件。
- **改动方案**：
  - `collect_single_device_data` 补齐 `"image_data"`（并统一走值形态识别，不再仅靠硬编码字段名白名单）。
  - 整设备事件触发（`field` 为空）时，在保留触发事件值的同时补拉该设备的其余最新指标快照，并沿用 1.3.3 的 `Input Status` 诚实状态口径。
  - `extract_trigger_candidates` 改用 `agent.schedule.parsed_event_filter()` 统一遍历 `any` + `all`（兼容旧版 `sources` 与 `event_type/device_id`），同时覆盖：
    - `event_filter` 中 `field` 为 `None`/空的整设备源；
    - 资源回退分支中的 `ResourceType::Device`（`--device-ids` 绑定），使 `build_synthetic_event_data` 能为整设备资源解析最新指标或触发整设备快照采集。

### 2.2 A2：基于“值形态”判定图片，消除误跳过

- **问题根因**：
  - `crates/neomind-agent/src/ai_agent/executor/data_collector.rs`（`is_image_metric`）只要指标名包含 `"image"` 就返回 `true`，导致 `metadata.image_id`、`image_count` 等非图片标量字段被误判为图片指标，提取结果返回 `Ok(vec![])` 后触发 `executor/mod.rs`（`execute_internal` 空事件跳过分支）。
  - 对任意 `http://` / `https://` 字符串返回 `true`，存在将 `firmware_url` 等普通链接误识别为多模态图片的风险。
- **改动方案**：
  - 改为以**值形态**为核心判定依据：仅当值符合 `data:image/...`、合法图片 base64 载荷，或明确的图片路径 / MIME 特征时才判为图片。
  - 字段名包含 `"image"` 但值为标量 ID、计数或普通非图片文本时，按普通指标处理，不再误入图片提取与跳过逻辑。
- **上下游注意**：
  - 核查 `data_collector.rs` 中 `is_image_metric` 的全部调用点，确保均传入真实指标值。
  - 同步更新 `test_is_image_metric` 单测契约，区分真实图片载荷与普通字符串/标量 ID。

### 2.3 A3：MQTT 与 Webhook 适配器改为“先批量写库，再发事件”

- **问题根因**：
  - `crates/neomind-devices/src/adapters/mqtt/handling.rs`（`handle_mqtt_notification` 指标提取循环）按指标逐条写入并逐条派发事件，同一批次后续字段（含图片）尚未落库时，第一条指标已触发 Agent 执行。
  - `crates/neomind-devices/src/adapters/webhook.rs`（`process_webhook` / `emit_metric_event`）存在更严重的时序倒置：先调用 `self.event_tx.send(DeviceEvent::Metric)`，后执行 `storage.write(...)`，最后再发布 `NeoMindEvent::DeviceMetric`。
- **改动方案**：
  - MQTT 与 Webhook 适配器统一改为两阶段处理：
    - **第一阶段（完整落盘与缓存）**：对同一次上报 `result.metrics` 中的所有指标依次完成 `convert_binary_to_url`、`metric_cache` 更新（MQTT）与 `storage.write(...)`。
    - **第二阶段（统一派发）**：第一阶段全部完成后，再统一派发 `event_tx.send(DeviceEvent::Metric)` 以及（Webhook）`bus.publish(NeoMindEvent::DeviceMetric)`。
- **上下游注意**：
  - 两阶段确保整设备监听收到第一条指标事件并进入 60s 冷却 / 1s burst-merge 窗口前，同批次的图片和其余指标已同时存在于 `metric_cache` 与时序库，A1 快照读取一次即可拿齐，后续同批事件由冷却窗口自然去重。

### 2.4 C1：修复上下文超窗重试发送旧 `input` 的 Bug

- **问题根因**：
  - `crates/neomind-agent/src/ai_agent/executor/tool_loop.rs`（`run_tool_loop`）在重试循环外构造了一次 `LlmInput`；触发 `LlmError::ContextOverflow` 后对 `messages` 原地调用 `compact_executor_messages`，但重试时仍重发旧的 `input.clone()`，导致压缩未生效且预算未重算。
- **改动方案**：
  - 将 `LlmInput` 构造移入重试循环内部，每次重试基于最新压缩后的 `messages` 重新构造 `input`。
  - 同步在循环内重算 `executor_response_budget`（`max_tokens`），确保重试请求符合当前剩余上下文窗口。

### 2.5 C2：给 Focused / Free 提示词字符串渲染加硬上限

- **问题根因**：
  - `crates/neomind-agent/src/ai_agent/executor/tool_prompt.rs` 中 `build_focused_resource_section` 与 `build_free_resource_section`（`Value::String(s) => s.clone()`）均无长度上限，超大字符串或未剥离的 base64 载荷会直接撑爆上下文（如 T4 线上 18 万 token 案例）。
- **改动方案**：
  - 为 Focused 与 Free 两种模式的字符串字段渲染统一增加安全字符上限与截断标记（明确标注原长度与已截断提示），禁止大载荷裸进文本提示词。

### 2.6 C3：事件路径独立重试谓词——永久性失败不重放、不清空冷却

- **问题根因**：
  - `crates/neomind-agent/src/ai_agent/executor/event_trigger.rs`（`execute_with_retry`）对永久性失败仍执行 `retries=1` 重放，导致熔断器双倍计次、用户收到双倍失败通知；同时将 `Failed` 记录包装成通用文案丢掉了原始 `record.error`，且外层在 `result.is_err()` 时无条件清除 `recent_executions` 冷却窗口。
  - **关键防坑**：不能裸复用 `executor/mod.rs` 中的 `is_transient_failure`——该函数服务于熔断器（`Active` vs `Error` 降级），将 `"already executing"` 与 `"daily run cap"` 也判为 `true`；直接复用会导致这两类场景误进事件重试或误清冷却。
- **改动方案**：
  - 在 `event_trigger.rs` 定义**独立的事件重试谓词**（如 `is_retryable_event_failure(error: Option<&str>) -> bool`），仅对真实瞬态传输/服务故障（网络错误、超时、限流、连接重置等）返回 `true`。
  - **严格保留** `execute_with_retry` 现有的 4 条防重放守卫：
    1. `daily run cap` 拒绝 → 直接返回跳过（不重试、不清冷却）；
    2. `already executing` 并发占用 → 直接丢弃（不重试、不清冷却）；
    3. `is_empty_event_skip` 空数据跳过 → 直接返回（不重试）；
    4. 已产生成功副作用（`actions_executed.iter().any(|a| a.success)`）后的失败 → **绝不重放、不清冷却**（防重复发告警/控设备）。
  - 将 `execute_with_retry` 返回值改为显式枚举（如 `EventRetryOutcome { Completed, Skipped, TransientFailure, PermanentFailure }`），保留原始 `record.error` 分类结果：
    - 仅 `TransientFailure` 允许重放 1 次并在最终失败后清除 `recent_executions` 冷却；
    - `PermanentFailure` 0 次重放且保留冷却窗口（并与 `was_probe` 探活退避协同）。

### 2.7 D1：执行记录仅存轻量输入摘要

- **问题根因**：
  - 排障需要知道当次执行实际拿到了哪些输入、是否走视觉路径以及跳过原因，但线上 `agents.redb` 已达 295 MB，不能在执行记录中重复落盘原始图片字节或大 payload。
- **改动方案**：
  - 在 `crates/neomind-storage/src/agents.rs` 的 `AgentExecutionRecord`（或其 `DecisionProcess`）追加带 `#[serde(default, skip_serializing_if = "Option::is_none")]` 的轻量结构化摘要字段：采集指标数、图片是否提取及来源字段名、是否命中 `vision_path`、跳过原因码，不存图片二进制/base64 正文。
  - 通过 `crates/neomind-api/src/handlers/agents.rs` 的 `AgentExecutionDetailDto` 透出。
- **上下游注意**：
  - `agents.redb` 实际使用 `serde_json` 序列化，追加带默认值的可选字段不改 schema 版本，满足 Gate G6 升级与回滚兼容。
  - **切勿改错结构体**：不要把该摘要写入 `AgentMemory.journal` 里的 `ExecutionRecord`，以免随历史日志注入每次执行的 Prompt。

### 3.2 B2：重写 `agent-management.md` 4 步创建 SOP 与 5 类场景模板（严控 Token 体积）

## 4. PR 3：视觉工具全失败状态机改造（P2，独立 PR）

### 4.1 D2：将执行收尾二分状态机改造为支持 `ExecutionStatus::Partial`（未判定）

- **现状与定位**：
  - 虽然 `neomind-storage` 中已定义 `ExecutionStatus::Partial` 枚举变体且 API 层已有序列化映射，但 `executor/mod.rs`（`execute_agent` 收尾逻辑）目前仍是 **`Completed | Failed` 二分状态机**，没有任何运行期路径产出或显式处理 `Partial`。
  - 因此本 PR 的核心工作是**改造执行收尾状态机及其下游分支**（不是简单“对齐现有路径”），独立成 PR 做完整回归。
- **改动位置**：
  - 后端：`crates/neomind-agent/src/ai_agent/executor/tool_result.rs`（`build_tool_result`）、`crates/neomind-agent/src/ai_agent/executor/mod.rs`（`execute_agent` 收尾状态机、stats、熔断、`AgentExecutionCompleted` 事件广播）、`crates/neomind-agent/src/ai_agent/executor/command_executor.rs`（`dispatch_agent_notifications`）。
  - 前端：`web/src/types/agent.ts`、`web/src/pages/agents-components/AgentExecutionTimeline.tsx`、`web/src/i18n/locales/{zh,en}/agents.json`（纯类型与 UI 映射，零新增依赖，不影响前端首屏 Bundle Budget）。
- **状态机改造与全链路语义锁定**：
  - 当本次执行依赖看图工具获取画面且所有看图调用均失败时：
    - `execute_agent` 收尾状态机由 `Completed | Failed` 二分扩展为显式三分（`Completed | Partial | Failed`），产出 `ExecutionStatus::Partial`、写入 `decision_process.stop_reason = "vision_tools_failed"` 与“未判定”结论前缀，禁止模型在未看到图像时自由发挥输出“现场正常 / 无异常”。
    - **显式处理 `Partial` 的全部下游分支**：
      - `NotifyOn::Judgment`：严禁放行告警（绝不满足 `Verdict: criteria met`）。
      - `NotifyOn::Failure`：视为未成功完成，允许向运维发送失败/未判定通知。
      - `consecutive_failures` 熔断器与 `update_agent_stats`：不重置失败计数、不计入 `successful_executions`（连续视觉工具永久失败可正常触发退避/熔断）；`AgentExecutionCompleted` 事件广播 `success: false`。
      - `event_trigger.rs`（`execute_with_retry`）：对 `Partial` 明确不重放、不清空冷却。
  - 前端补齐 `ExecutionStatus` 中的 `'Partial'` 类型、时间线警告色图标样式与中英文 i18n 文案（如 `部分完成 / 未判定` / `Partial`），避免 UI 状态徽章掉出兜底分支。
- **验收测试**：
  - [ ] 后端单测：模拟看图工具全部返回错误时，执行状态落入 `ExecutionStatus::Partial`（`stop_reason = "vision_tools_failed"`），不输出“正常”结论，不触发 `Judgment` 告警，不重置 `consecutive_failures`，`execute_with_retry` 不重放。
  - [ ] 前端单测 / 类型检查：`ExecutionStatus` 渲染 `'Partial'` 状态无报错且中英文文案完整。
