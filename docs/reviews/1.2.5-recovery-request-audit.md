# 恢复版验证包复核与请求设置修复

复核输入：`recovery-verify@95929a96` 的报告、smoke/paired/shard A/B 原始 scores 与执行日志。代码基线为 `fix/1.2.5-chat-regression-recovery@ce93d32e`。本次没有修改外部验证报告或原始证据。

## 当前结论

恢复候选没有通过模型质量验收。此次修复的是实际请求参数丢失这一确定的配置错误；它不能证明提示层恢复有效，也不能证明重写架构优于旧版。此前把少量用例改善解释成“完全治愈”缺乏充分证据，不应继续沿用。

### 参数不等同于报告声明

原始日志记录了 841 次发往 llama.cpp 的流式请求：smoke 43、paired 261、shard A 277、shard B 260。全部是 `temperature=0.3, top_p=0.75, max_tokens=8192`，不是报告声明的 `1.0/0.95`。日志未记录 top_k/min_p；不能推断它们的实际值。

配置丢失链路：eval 创建后端实例并保存采样设置 → 实例转换成只携带端点/模型/能力的 LlmBackend → Agent 创建的 LlmInterface 沿用本地默认值。前端激活后端也复制了同样的有损转换。另一个遗漏是 llama.cpp 适配器不序列化 GenerationParams.top_k。

这些路径不是 c7fb 独有，不能据此把所有行为下降归因于参数变化。仍需对参照版和修复版捕获真实请求，用相同有效参数重新比较。min_p 没有逐请求字段，需单独记录并统一模型服务设置，不能宣称本补丁已验证 min_p=0。

## 本补丁的边界

- 绑定后端时携带不含凭据的请求设置快照：temperature/top_p/top_k及thinking控制。全局active变化不会暗中改变另一已绑定会话的请求设置；显式重绑时刷新快照。
- 新建、恢复会话及前端激活后端使用同一配置来源；CreateSessionOptions显式温度覆盖优先。
- llama.cpp流式/非流式请求发送top_k；记录流式请求top_k。普通直接配置的Agent尊重已有AGENT_TOP_P配置入口。
- 普通runtime切换清掉先前后端默认值，避免残留。没有新增关键词意图判断、自动催执行、重复调用硬断或新的任务终止策略。
- 不修改max_tokens预算策略、接口JSON字段、前端事件协议、工具结果结构。设置页不需要迁移；已保存的参数开始真正参与请求，输出可能因此变化，必须复测。
- HTTP测试覆盖实际请求体，不使用模型回答质量作为模拟服务测试断言。它只能证明配置传递与会话隔离，不能替代真实模型验收。

## 真实模型验收尚未执行

用户已授权必要时停止远端NeoMind后端LLM释放资源，但当前云环境没有SSH TCP出口：`vpn_configured=false`，TCP授权为空，平台TCP代理连接被拒绝。本轮没有连接服务器、停止服务或启动远端评估。工作区也没有可用Spark权重或本地模型服务。

接通后应保留参照与候选两个release二进制及commit SHA；记录GGUF校验和、llama-server版本、上下文、完整采样和thinking设置、并发、seed与预算。先双边验证实际请求参数，再对新损失/新获胜/固定通过控制用例多轮交错A/B，最后138条全量。Mac与T4分别比较，不混为同机结果。产品通过率将超时计为失败；同时报告诊断通过率、延迟、工具调用数与资源占用。不得仅凭减少干预代码或单条成功把重写称为优化。

对照尤其要区分两件事：先将候选设为旧版日志确认的有效采样值，统一服务端其余采样，比较架构本身；再独立测配置修复后的目标参数。若要在目标参数下比较旧架构，需要给参照分支应用相同的最小参数传递补丁，并明确标记为patched-reference，不能把它冒充原发布二进制。只让候选实际应用1.0/0.95、旧版仍实际发送0.3/0.75，不是受控架构对照。
