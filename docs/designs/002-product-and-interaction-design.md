## 1. 用户与他们的世界

### 1.1 三类角色

| 角色 | 是谁 | 特征 | 对智能能力的真实诉求 |
|------|------|------|----------------------|
| **经营者/运营者** | 厂长、能源/设备管理员、物业经理、连锁门店老板 | 不写 prompt，不看日志；手机+告警是主界面 | "别让我派人去盯/去抄/去查"，出事第一时间知道，没事别烦我 |
| **实施者/集成商** | 给客户装 NeoMind 的工程师 | 会配设备建仪表盘，关心可复制交付与成本可解释 | "半天给客户交付一套能跑的方案，AI 花费我能算清楚报给客户" |
| 开发者 | 写扩展/调 API 的极客 | 已被 SDK/API 服务的群体 | 不是本次设计目标 |

**设计目标是前两类。** 一个硬校验：本文的每个交互设计，都必须能向一位厂长解释清楚（§4 逐条过这个标准）。

### 1.2 用户嘴里的任务（JTBD 原声）

- "冷库温度半夜有没有超标时段，早上告诉我" —— 环境监测 · 每日报告
- "车间电耗这周比上周高了三成，帮我看看是哪条线的事" —— 能耗 · 排查
- "这块仪表每 15 分钟抄一次数进系统" —— 抄表（摄像头读数或 Modbus 直读皆可）
- "每天统计各产线的良品数，异常批次标出来" —— 生产数据 · 例行整理
- "包装台画面里有没有错装漏装，有的话记下来" —— 视觉质检 · 巡检
- "温度超过 8℃ 持续十分钟就叫我，最好先看看是不是冷库门没关" —— 阈值盯守 · 带排查
- "装卸区有车停超过 20 分钟就叫人处理，叫之前先自动核对是不是预约车辆" —— 实时画面盯守 + 智能体处置
- "冷库现在整体什么情况？"——去问"懂冷库的那个值守项"要一份已消化的结论，而不是自己啃原始指标 —— chat 调度智能体
- "现在的画面/数据里有什么异常吗？" —— chat 临时问一句

### 1.3 四种雇佣模式（核心业务抽象）

把上面的 JTBD 归类，用户其实只在**雇佣** NeoMind 做四种事：

| 雇佣模式 | 用户原声 | 频率 | 单次价值 | 失败的代价 | 交付物 |
|----------|----------|------|----------|-----------|--------|
| **替我看** | "每15分钟抄一次表" | 高（分钟级） | 低 | 数据旧了/错了 → 治理一下 | 结构化数据 |
| **替我盯** | "温度超标十分钟就叫我" | 事件驱动 | 中 | 漏报/误报的代价**随场景不同**：灵敏度偏好按看护项可配（漏报敏感型 / 误报敏感型） | 即时通知+依据 |
| **替我查** | "查查能耗为什么高" | 低（周/月级） | 高 | 查错方向 → 人力浪费 | 结论+已采取的动作 |
| **替我报** | "早上给我夜间摘要" | 低（日/周级） | 中 | 报告没人看 → 价值感流失 | 人读的报告 |

这张表是**全文档的定价表**：频率×单次价值×失败代价，决定了每种模式该用什么技术、该收多少钱、该把产品功夫花在哪。技术概念（算子/规则/智能体/任务，见 §7）只是四种雇佣模式的执行 substrate，**对用户不可见**。

**场景中立原则**：雇佣模式按"用户与任务的关系"划分，不按行业、也不按数据类型划分。摄像头只是众多输入之一——与温度传感器、电表、Modbus 寄存器、天气 API 同级；视觉理解是重要能力，不是设计主角；安防只是模板库里的一个分类。本文所有机制（看护项/判定链/纠错/价值回顾）对任何数据源组合同等成立。

## 2. 价值逻辑

### 2.1 价值公式与 AI 选位

```
净价值 = 被替代的人力 × 频率 − 运行成本 − 出错成本（错误率 × 单次错误损失）
```

逐模式套用：

| 模式 | 人力替代 | 运行成本策略 | 出错成本策略 |
|------|----------|--------------|--------------|
| 替我看 | 抄表员/巡检工时 | **每次成本必须≈0** → 确定性模型为主；LLM 仅承担开放语义（"整洁度"），且靠防抖把频率压到价值可覆盖 | 保旧值+标过期+置信度可见，错误不进入下游动作 |
| 替我盯 | 值守/监控工时 | 规则做闸门（零成本高频），AI 只在语义判断或多源综合判断环节 | 灵敏度按看护项配置：漏报敏感型（连续 N 次确认才触发）或误报敏感型（阈值+冷却），通知必带依据 |
| 替我查 | 老师傅排查工时 | 低频高值 → 多轮 LLM 工具循环完全划算 | 结论附推理过程与依据，动作需确认或留审计 |
| 替我报 | 例行报告工时 | 一次大调用+历史注入 | 报告开篇给"要点结论"，可追溯每条到原始数据 |

**VLM 与传统 CV 的选位**（用户说"用 VLM 替代 CV"时的诚实答案）：

| | 传统 CV（扩展模型） | VLM 算子 | 级联（CV 筛 + VLM 判） |
|---|---|---|---|
| 类目 | 封闭，检测什么先训练什么 | **开放，改一句话就换需求** | CV 出候选，VLM 出语义 |
| 频率 | 帧级（25fps），近零成本 | 秒级采样，每次都是推理成本 | CV 帧级 + VLM 仅候选出现时 |
| 擅长 | 精确计数/定位框 | 分类判断/合规性/描述/开放词汇 | 两全其美，成本居中 |
| 典型 | 人形/车辆/安全帽检测 | "地面是否整洁""是否违规堆放""仪表读数" | 人出现(CV)→着装是否合规(VLM) |

"替代"的准确表述：VLM 替代的是**开放类目、秒级容忍**的那部分 CV 任务；帧级精确检测仍是传统 CV 的地盘；最常用的形态是级联——CV 当廉价触发器，VLM 当语义裁判。用户改需求只改一句话而非重训模型，这是 VLM 路线的核心卖点，也是"替代"叙事的真实支撑点。

**推论**：LLM 不是卖点，是成本项。产品话术永远讲"替你省了什么"，不讲"我们用了大模型"。

### 2.2 价值可感知化：价值回顾

价值必须被看见才会续费。平台每月自动生成**价值回顾**（进报告/通知渠道）：

> 本月：替你值守 720 小时 · 抄表 2,880 次 · 发现异常 12 起 · 平均响应 40 秒 · 估计替代人工 36 工时

数据全部来自现有执行记录的聚合，无新采集成本。这是把"后台运行的技术"翻译成"经营语言"的月度触点。

### 2.3 定价与成本可见性（面向实施者）

- 每个雇佣项的运行成本实时可见："这个抄表任务：本地模型，每天 96 次，占用推理约 20 分钟"；云 backend 则显示次数与 token。
- 实施者可以给客户讲清楚账——这决定了集成商敢不敢开 AI 功能。预算护栏（每日上限、熔断）是**默认开启**的，防的就是"客户月底收到账单惊喜"。

## 3. 业务逻辑

### 3.1 核心业务对象：看护项（Care Item）

现状的问题：用户面对的技术对象是 "Agent"（要理解 Focused/Free、schedule type、event filter）。用户的业务对象从来不是这些，是——

```
看护项 = 我关注什么（目标：哪台设备/哪个区域/哪个指标）
       + 我要什么（雇佣模式：看 / 盯 / 查 / 报）
       + 交付给谁（仪表盘字段 / 通知给谁 / 报告渠道）
       + 出了事怎么办（只通知 / 通知+执行命令 / 先查再说）
       + 多久一次（节奏：实时 / 每15分钟 / 每天8点 / 有事件时）
```

五个问题的答案就是创建表单的全部字段。**用户声明目的，平台编译手段**：后端把看护项编译成 算子+规则+智能体 的组合拓扑（"替我看"→算子；"替我盯"→算子+规则+通知，必要时升级为"规则→智能体"处置；"替我查"→事件触发的智能体；"替我报"→定时任务+报告模板），编译结果以"工作方式"一页大白话回显（§4.1），但用户**永远不需要选择执行方式**。

**实时盯守 + 智能体处置**（"建一个实时 VLM 监控、让它做智能体工作"的解法，"替我盯"的完整形态）：

```
盯档算子（采样间隔可配 2-10s，输出状态枚举）
  → 语义规则（状态进入"违规"并持续 N 秒，for_duration 现有能力）
    → 触发智能体（携带触发证据：关键帧 + 当时的判定与置信度）
      → 智能体多步处置（如：核对是否预约车辆 → 调取关联数据 → 决策）
        → 执行动作（通知/下发命令）+ 结论回写为数据源
判定链贯穿全程：用户点开任何一环，都能看到"它看到了什么、为什么行动"
```

两个必须写死的边界：其一，**"实时"= 秒级循环，不是帧级**——边缘 VLM 单帧推理 1-5s，创建时明示采样间隔与预期响应时延，不假装 fps；帧级需求用传统 CV 扩展承接（级联见 §2.1）。其二，**证据透传**——智能体被触发的那一刻就拿到触发帧与判定作为首轮上下文，它与用户看的是同一份现场，不必重新感知一遍。

**一份槽位结构，三种前端**（"对话即创建"的语义底座）：理论上一段对话就该完成创建。让对话可靠地产出正确的看护项，靠的不是更聪明的模型，而是平台把创建协议语义化为三层结构：

| 层 | 结构 | 作用 |
|----|------|------|
| 槽位结构 | 五问 → 类型化槽位表（目标=资源引用；模式=枚举 看/盯/查/报；交付=枚举+路由；处置=枚举；节奏=触发规格），每槽带必填性/默认值/校验 | 模型做"填表"而非自由发挥；缺哪个槽，对话就只问哪个问题 |
| 实体结构 | 语义资源目录：设备/指标/通知渠道/已有看护项统一携带 名称·别名·位置·能力标签·单位 | "冷库"→temp-01、"张经理"→渠道，落定为真实 ID 并回显，绑定错一眼可见、可纠正 |
| 回显结构 | 草稿确认卡：落定实体 + 编译预览（"工作方式"大白话）+ 试跑结果 | 创建的最后一步永远是一张可确认、可改槽、可试跑的卡 |

**草稿-确认协议**（安全边界）：对话永远不直接创建——AI 只产出草稿卡，显式确认才落库；草稿在会话内持久，"把通知改成李经理"这类追问即改槽。沉淀（§4.1 入口三）是同一协议的特例：预填草稿再确认；向导（入口二）与对话（入口四）渲染的是同一张卡。

> 与 001 的关系：看护项是 001 中"任务/智能体/算子"之上的产品层封装；`/api/agents` 等底层 API 保留给实施者直用（双入口：简单入口=看护项向导，高级入口=现有 agent/transform 编辑器）。

### 3.2 判定链：每一次自动行为都要能回答"为什么"

告警/报告/数据字段，每个自动产出生成时记录判定链：

```
冷库温度异常通知 2026-09-22 23:41
判定链：
  ① 温度传感器 temp-01 读数 9.4℃（连续第 3 次超 8℃ 阈值）   [查看曲线]
  ② 门磁 door-01：关闭（排除"门没关"这个常见原因）           [查看记录]
  ③ 压缩机 power-03（Modbus）：运行电流偏低                  [查看原始值]
  ④ 综合判定：持续超标 + 门已关 + 电流偏低 → 疑似制冷故障
     （置信度 0.87）
  → 通知：张经理（App 推送）｜联动：已下发启动备用制冷｜留证：近 1 小时曲线快照
```

（同一机制对摄像头输入同样成立：①抓帧 → ②画面分析"检测到错装 1 件，置信度 0.93"附原图框选 → ③批次规则命中 → 通知+记录。判定链不关心输入是遥测还是画面。）

判定链 = 原始输入（证据）+ 每步判定（谁判的、依据、置信度）+ 最终动作。它是三样东西的载体：**用户信任的来源、纠错的入口（§4.3）、合规审计的记录**。落地形态 = 现有执行记录的结构化扩展（见 §7 映射）。

### 3.3 纠错样本：越用越准的业务闭环

AI 判断错误时，用户的纠正行为要变成资产：

```
用户看到：整洁度 = "整洁"（实际画面明显杂物）
用户动作：就地标注 "错了，应为：混乱"（30 秒内完成，不离开当前页面）
系统行为：① 纠正样本入该看护项的样本库（原图+用户标注+当时判定）
          ② 下次运行 prompt 自动携带最近 K 条纠正样本
          ③ 界面可见 "已根据你的 3 次纠正优化"
```

这是把"模型不准"从退货理由变成使用粘性：**用户教得动系统**。样本库随看护项导出/复制（实施者把调教好的看护项做成模板交付，见 §4.1）。

### 3.4 反馈闭环（盯守结果的质量运营）

告警不做工单化流程——认领/派单/升级链属上层业务系统，**移出本设计范围**（2026-09-22 评审：平台做 AI 内核，不做业务流转）。平台负责的闭环只有两个：

1. **误报反馈**：标记误报 → 自动记入该智能体的纠正样本（§3.3）→ 累计 N 次建议调整判定阈值——告警质量可运营；
2. **联动回显**：判定链末尾如实展示系统已执行的动作（通知了谁、下发了什么命令），事后可查，无需人工补录。

## 4. 交互逻辑（关键时刻逐一设计）

每个小节先给用户的一句话心智，再给界面。硬校验标准：**能否向厂长解释**。

### 4.1 创建时刻 —— 魔法时刻，三个入口

**心智：我不是在配置系统，我在雇一个值班员。**

**入口一：模板库**（经营者的默认路径，30 秒完成）

```
┌─ 看护模板（按行业/场景分类，以下是跨行业示例集）──────┐
│ [温度异常盯守]  [能耗超标预警]  [仪表自动抄表]        │
│ [产量日统计]    [视觉质检巡检]  [每日运营摘要]        │
│ （安防类模板是其中一个分类，按需安装）                │
│ 选中 → 只问两件事：                                    │
│   ① 用哪个设备/数据源？                               │
│   ② 通知谁？                                          │
│ → 创建完成，立即试跑一次给你看                         │
└──────────────────────────────────────────────────────┘
```

模板 = 预编译的看护项（含 prompt、输出 schema、判定规则、通知路由），由官方/集成商沉淀。实施者的商业路径：交付即模板化。

**入口二：说一句 + 当场试跑**（核心差异化交互）

```
┌─ 新建看护项 ────────────────────────────────────┐
│ 数据源：[cam-01 ▾]（预览当前画面；               │
│          选温度/电表等数据源时预览最新读数曲线）   │
│ 你要它做什么：                                   │
│ ┌─────────────────────────────────────────────┐ │
│ │ 看看包装台画面有没有错装漏装，                │ │
│ │ 统计数量并标记批次状态                       │ │
│ └─────────────────────────────────────────────┘ │
│           [试跑一次]                             │
│ ──────────── 试跑结果 ────────────               │
│ 漏装：1 件（置信度 0.91）  [查看依据：原图+框选]  │
│ 建议输出字段：漏装数 · 错装数 · 批次状态          │
│ 节奏：变化后 30 秒内最多一次    [调整]            │
│ 交付：仪表盘字段 ✓   通知：漏装时→张经理          │
│           [保存并开始]                           │
└─────────────────────────────────────────────────┘
```

**试跑（dry-run）是交互核心而非 API 附属**：用户在承诺之前先看到 AI 用真实输入给出的真实输出——这一眼就是购买决策。输出 schema 由平台从用户那句话预生成，用户只确认。

**入口三：从对话沉淀**（留存放大器）

用户在 chat 连续问了两次同类问题（"冷库温度现在正常吗？"），chat 末尾出现：

> 这个问题要我以后替你值守吗？温度超标十分钟就通知你。 [创建盯守]

一键把对话能力固化为看护项（预填 prompt 与触发源，复用入口二的确认页）。**chat 从"问答工具"升级为"看护项的发现入口"**——这是 NeoMind 独有的交互资产：别的平台 chat 和自动化是两个世界，这里对话是自动化的漏斗上游。

**入口四：对话即创建（入口二的对话形态）**

```
用户：帮我盯着冷库，超过8度持续十分钟就叫张经理，
      最好先看看是不是门没关
AI  ：[草稿卡] 目标：冷库·温度(temp-01) + 门磁(door-01)
      模式：盯 ｜ 节奏：超标持续10分钟 ｜ 通知：张经理(App)
      处置：先核对门状态，排除后再通知
      （缺省假设已标注：按"持续10分钟"理解）
                     [试跑一次]  [确认创建]
用户：改成李经理，其余确认
AI  ：已创建"冷库温度盯守"。首跑已开始，30 秒后回你结果——
      以后直接问我"冷库怎么样"就行（§4.6）
```

创建完成的那一刻，它立即成为 chat 可调度的对象（§4.6）——**创建与问询在同一对话里闭环**，用户不离开聊天界面完成"想→建→用"全程。

### 4.2 信任时刻 —— 每个输出带证据

**心智：它说的每句话，我能亲眼核。**

- 所有 AI 字段在仪表盘/详情处可点开 → 原始输入（图/数值）+ 判定依据 + 置信度。
- 低置信度（可配阈值）不直接当真：显示为"待确认"色，可触发"转人工确认"而非直接进判定链下游。
- 首次运行的前 N 次（默认 10 次）标记"磨合期"，界面提示"它还在学习你的标准，多纠正几次会更准"——把早期不准从扣分项变成预期管理。

### 4.3 纠错时刻 —— 30 秒教会它，下次就改

**心智：我说一次，它记一辈子。**

- 纠错入口就在结果出现的地方（判定链详情/仪表盘字段/报告条目），流程：点"不对" → 选/填正确值 → 完成。
- 纠正后可立即"重跑一次"验证改善——用户当场看到系统听话，这是最强的留存时刻。
- 纠错记录进样本库（§3.3），看护项详情显示"已被纠正 3 次，全部生效"。

### 4.4 运行时刻 —— 智能体 tab 原地升级（管理与运行状态合一）

> 命名与结构决定（2026-09-22 评审）：**菜单、页面、tab 结构全部沿用现状**（智能体/记忆/技能/工具），不新增 tab、不新造入口——曾设想的独立"值守总览" tab 因与智能体列表约七成重复而否决。运行态（在岗/降级/新鲜度/今日动作）直接长在现有「智能体」tab 的卡片上；**算子是智能体的一种类型**——列表不分组、不出现"算子"字样，四种雇佣模式徽章（替我看/盯/查/报）即类型表达。"看护项"降为内部设计词汇，**用户可见名词统一为"智能体"**。

**心智：我的值班员们今天都在岗吗？**

```
┌─ 智能体（现有 tab 原地升级）────────────────────────────┐
│ 冷库温度盯守      ● 在岗   当前 -18.2℃ 正常       [详情] │
│ 车间能耗盯守      ● 在岗   本周环比 +3% 预算内     [详情] │
│ 包装台视觉质检    ◐ 降级   上次成功 40分钟前(已标旧值) [详情] │
│ 仪表自动抄表      ● 在岗   今日 96 次·本地模型     [详情] │
│ 每日运营摘要      ● 在岗   明早 08:00 下一期      [详情] │
│ 本月：值守 720h · 作业 2,880 次 · 异常 12 起 · ≈36 工时   │
└─────────────────────────────────────────────────────────┘
```

每张卡片四要素：**在岗状态**（在岗/降级/暂停——降级=连续失败熔断，一眼看懂"它暂时干不了活在自愈"）、**新鲜度**（上次成功何时）、**今日动作**（干了什么/花了什么）、详情。底部一条价值回顾常驻（§2.2）。**没有任何一处出现"agent/transform/mode/filter"字样。**

**详情与统一新建**（2026-09-22 二次评审：三段式重构）：新建仍为无向导的单页表单，但重排为三个带标号的分区——**① 身份**（名称/描述/模型）→ **② 能力**（类型四选一为总开关，模式专属区随类型变化：替我看=指令+输出字段+护栏，盯=指令+判定阈值+通知，查=提示词+工具范围，报=模板+渠道）→ **③ 运行策略**（节奏确认+通知路由+按类型过滤的高级折叠）；防抖/平滑/预算/超时合并为能力段的"护栏"组；**试跑为吸底 CTA**（仅看/盯类型显示），结果卡在右栏。解决首版的四个混乱来源：输出区插在模式卡与基本信息之间、调度区离模式区过远、高级项不随模式变化、试跑埋在表单中部；详情沿用现有 AgentDetailPanel 四 tab（总览/执行历史/记忆/留言）——总览顶部新增"运行状态/输出字段"两个 section，执行历史沿用现有时间线并给每条加判定链入口，记忆 tab 新增"纠正样本"（界面稿见 docs/designs/ui-mockup.html ②/②·B，带保留/新增/调整增量标记）。

### 4.5 行动时刻 —— 告警详情：可解释 + 可反馈

**心智：出事了，这一页让我三分钟搞清楚"为什么"；不对就一键教它。**

告警推送点开 = 判定链（§3.2 全文）+ 依据（曲线/原图/原始值）+ 已执行联动的如实回显（通知了谁/下发了什么命令）。人工动作只有**反馈**：[标记误报]（自动入纠正样本，累计 5 次建议调整判定阈值）/ [确认有效]。不设认领、派单、升级链——那是业务系统的职责，平台通过消息渠道与 API 对接即可。

### 4.6 问询时刻 —— chat 是调度台，不是复读机

**心智：它背后有一队专家（看护项），它负责问对人，而不是自己现场学一遍。**

用户在 chat 里提问时，AI 按**信息金字塔**逐层下探，只在前一层不满足时降层：

| 层 | 动作 | 成本 | 用户感知 |
|----|------|------|----------|
| ① 查现成结论 | 读看护项最近的结论/输出字段 | 零，毫秒 | 秒答，标注"截至 3 分钟前"+ 可点开判定链 |
| ② 现场跑一次 | 触发该看护项按需执行 | 一次执行，10 秒~分钟 | "我让冷库值守现查一遍…"，进度实时回传 |
| ③ 原始工具兜底 | 自己查设备/数据 | 视工具而定 | 回答更慢、只引用原始数据 |

三个配套设计：

- **选取靠用户自己的词汇**：chat 的可选专家列表由看护项注册表实时生成，工具名即用户命名（"冷库温度盯守"）——用户怎么叫它，AI 就怎么找到它，无需配置同义词。
- **同源一致**：chat 引用的结论与智能体页是同一份执行记录，答案附判定链引用——不会出现"chat 说正常、仪表盘说异常"。
- **闭环回沉淀**：用户对同一看护项反复"现场跑"（第②层）达到阈值时，出现"要我把它变成每 5 分钟自动查吗"（衔接 §4.1 入口三）——问询流量是看护项的发现漏斗。

## 5. 用户使用逻辑（旅程与渐进阶梯）

### 5.1 渐进参与阶梯（产品的成长路径）

```
看仪表盘（被动接收） → chat 问一句（主动好奇） → 定一条规则（尝到自动甜头）
      → 建看护项（完成雇佣） → 沉淀更多/调教/看价值回顾（深度依赖）
```

每一级都是下一级的入口（chat 问→沉淀；规则触发→"要不要让 AI 判断得更聪明"→看护项）。**产品目标：把用户沿阶梯往上送，每一级的首次体验都有对应的魔法时刻**（chat 的首答、看护项的试跑、第一个月的价值回顾）。

### 5.2 四条关键旅程（各配成败标准）

**旅程 A · 冷启动（第 1 天）**：装好→接上数据源（温湿度/电表，或摄像头）→模板库点"温度异常盯守"→选设备选通知人→**30 秒后收到一条演示通知**（系统注入一条模拟读数验证整条链路）→装第二个。
✅ 成败：首日收到第一条真实/演示通知；❌ 失败模式：让用户先读概念文档。

**旅程 B · 替代人工（第 1 周）**：带着人抄一次表→对系统说"照这个格式每 15 分钟抄一次"→试跑对比人工值→开启→仪表盘自动长数据→次晨摘要里看到抄表记录。
✅ 成败：一周后人工抄表动作消失；关键卡点：试跑对比时用户发现读错→当场纠错生效（旅程 D 兜底）。

**旅程 C · 沉淀（第 2 周起）**：chat 里重复问同类问题→出现"要我替你盯吗"→一键固化→智能体列表多一张卡。
✅ 成败：沉淀创建的看护项占比逐月上升（可埋点度量）；这是 chat→自动化的转化率，**本设计最重要的北极星指标**。

**旅程 D · 纠错与调教（持续）**：发现误判→就地纠正→重跑验证→看到"已根据你的纠正优化"。
✅ 成败：被纠正过的看护项 30 天留存显著高于未纠正的；纠错入口 30 秒内完成。

### 5.3 时序逻辑（用户什么时候打开什么）

| 时刻 | 用户行为 | 产品供给 |
|------|----------|----------|
| 每天 08:00（被动） | 收到夜间摘要 | 每日报告（替我报） |
| 告警瞬间（被动） | 点开查看/反馈 | 通知详情=判定链+依据+误报反馈（§4.5） |
| 随时（主动） | 打开智能体页巡一眼 | 状态/新鲜度/成本总览（§4.4） |
| 每周（主动） | 调整看护项 | 编辑+模板另存 |
| 每月（被动） | 收到价值回顾 | ROI 报告（§2.2） |

注意被动触点（摘要/告警/回顾）多于主动触点——**运营者的大部分体验发生在 NeoMind 之外（推送/短信/邮件），这些推送本身就是产品界面**，其质量（要点先行、证据可点、反馈可达）决定经营者的留存。

## 7. 对 001 的修订指令（技术附录的增补）

001 架构结论（算子落数据面、多源触发、输出契约、kernel 统一）**全部保留**，但需增补四项，均由本文 P0/P1 需求驱动：

1. **evidence 字段**：OperatorAutomation 输出携带证据引用（图片路径/来源 DataSourceId+值/框选坐标），随字段发布——判定链与点开核验（F3/F4）的数据基础。
2. **correction_samples**：看护项关联的纠正样本存储（输入快照+用户标注+当时判定+时间），prompt 组装时注入最近 K 条（F5）。
3. **判定链关联**：告警/报告条目 → 触发它的算子执行记录 → 原始输入证据，三层外键（F3）。
4. **执行记录增加雇佣模式维度**：价值回顾聚合（F10）与智能体页分组（F7）的查询键。
5. **看护项即 chat 工具**（F13）：动态工具目录（会话建立时由看护项注册表生成）+ invoke 进度中继 + 结论新鲜度标记——chat 调度智能体（002 §4.6）的技术底座。
6. **槽位化创建 IR 与语义资源目录**（F14/F15）：CareItemDraft 类型化槽位取代松散的 ParsedIntent；ResourceIndex 从 chat 内部实现升格为平台级目录服务（向导/chat/规则构建器三方共用），吸收 semantic_mapper 的 LOCATION_ALIASES 与 mapper.rs 别名词典作种子数据，用户纠正的别名持久化。

另：001 §8 评审清单追加一问——D8 看护项是否作为独立存储实体（建议：是，`care_items.redb` 或 automations 域新表，编译产物引用现有 agent/operator id）。
